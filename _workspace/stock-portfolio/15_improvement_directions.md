# 개선 방향성: 기록 도구에서 신뢰 가능한 자산 기록 시스템으로

작성일: 2026-07-17. 08(제품 로드맵), 09(제품 레벨 로드맵), 12(프로덕션 자동화)의 후속 문서다. 그 문서들이 "제품으로 여는 조건"을 다뤘다면, 이 문서는 **데이터와 계산 자체를 얼마나 믿을 수 있는가**를 중심에 놓고 다음 1~2년의 방향을 정리한다.

## 결론

Stocklio의 다음 단계를 결정하는 질문은 하나다: **"이 화면의 숫자를 의심 없이 믿을 수 있는가?"** 현재 구조는 이 질문에 세 지점에서 취약하다.

1. **역사가 없다** — holdings는 현재 포지션(수량, 평단)만 저장하고 매수/매도 이벤트를 기록하지 않는다. 평단 수정은 파괴적 갱신이라 실현손익과 매매 복기가 원천적으로 불가능하다.
2. **수익률 정의가 하나뿐이다** — 순입금 차감 방식은 MWR의 거친 근사다. 입출금 시점에 따라 같은 운용 성과가 다른 숫자로 보인다.
3. **다기기 동시 사용이 위험하다** — `PUT /api/state`가 전체 JSON blob을 조건 없이 덮어쓴다(last-write-wins). 폰과 데스크톱을 같이 쓰는 순간 데이터 소실이 실제로 일어날 수 있는 구조다.

이 셋을 해소하는 것이 어떤 신규 기능보다 우선이다. 기능은 나중에 붙일 수 있지만, 기록의 신뢰는 소급해서 만들 수 없다.

## 현재 상태 진단

### 강점 (지켜야 할 것)

- **공유 순수 도메인 레이어** — `src/domain/portfolio-core.js`의 계산 함수를 브라우저/로컬 서버/Vercel 함수 3환경이 동일하게 임포트한다. 계산 로직이 한 곳에 있다는 것이 이 프로젝트의 가장 큰 구조적 자산이다.
- **상태 버저닝** — `STATE_VERSION` 단일 상수와 마이그레이션 관행이 이미 자리잡았다 (현재 v6).
- **자동화 이중화** — 로컬 15분 루프(`server.mjs`)와 Vercel Cron(`api/cron/daily-snapshot.js`)이 같은 도메인 함수를 호출한다.
- **뷰 모듈 분리 완료** — `stocklio-app.js`는 1,573줄의 오케스트레이터로 줄었고 탭별 뷰가 개별 파일로 나뉘어 있다.
- **제약의 명문화** — 금융 조언 금지, 서비스 키 격리, private 데이터 경로가 CLAUDE.md에 강제되어 있다.

### 구조적 부채 (구체적 위치와 함께)

| 부채 | 근거 | 결과 |
|---|---|---|
| 거래 이력 부재 | `state-factory.js` — holdings에 `quantity`/`averageCost`만 존재, 트랜잭션 배열 없음 | 실현손익·배당 이력·매매 복기·세금 기록 불가. 스냅샷 재계산 불가 |
| 전체 blob 덮어쓰기 | `server.mjs:62` PUT 핸들러, `server.mjs:290` upsert — revision 검사 없음 | 다기기 동시 편집 시 조용한 데이터 소실 |
| 수익률 단일 정의 | `getNetInflowKrw` 차감 방식만 존재 | 입출금 타이밍에 성과 지표가 왜곡 |
| 시세 소스 단일 의존 | Yahoo 비공식 API만 사용 (`api/yahoo/*`, `market-data-service.js`) | Yahoo 차단/변경 시 가격 갱신 전면 중단 |
| 프론트 이중 스택 | vanilla JS 앱 + React/Craft.js 섬(`craft-dashboard.jsx`)이 이벤트로 통신 | 두 패러다임 유지비, 상태 동기화 버그 표면 |
| 스냅샷 결손 영구화 | cron 실패한 날의 스냅샷을 소급 생성하는 경로 없음 | 성과 그래프에 메울 수 없는 구멍 |

## 개선 축

### 축 1: 거래 원장(Transaction Ledger) 도입 — 데이터 자산화의 핵심

가장 큰 구조 변화이자 가장 큰 가치. holdings를 "진실"에서 "파생값"으로 강등시킨다.

- state에 `transactions[]`를 추가한다: `{ id, date, type: buy|sell|dividend|split|fee, ticker, account, investor, quantity, price, fee, tax, currency, note }`
- **마이그레이션(STATE_VERSION 7)**: 기존 각 holding에서 가상의 opening 트랜잭션(현재 수량, 현재 평단)을 생성한다. 과거를 발명하지 않고 "이 시점부터 원장이 시작됐다"를 정직하게 표시한다.
- **점진 전환 전략**: 1단계에서는 원장을 병행 기록하며 holdings와의 정합성을 검증만 하고, 2단계에서 holdings 계산을 원장 파생으로 교체한다. 도메인 함수 `deriveHoldings(transactions)`가 순수 함수로 3환경에 공유된다.
- 얻는 것:
  - 실현손익과 종목별 매매 히스토리 (매도 시 원가 배분: 평균법 기본, 추후 선입선출 옵션)
  - 배당 이력의 구조화 — 현재 cashflow에 섞여 있는 배당을 종목 귀속으로 기록
  - 주식분할/병합(corporate action)의 올바른 처리 — 지금은 평단을 손으로 고쳐야 한다
  - 양도소득세 신고용 **기록** 내보내기 (계산 조언이 아니라 원장 그대로의 기록 — CLAUDE.md 제약과 충돌하지 않음)
  - 임의 시점 포트폴리오 재구성 → 스냅샷 소급 재계산 가능 (축 3의 backfill과 연결)

### 축 2: 수익률 계산의 정합성 — TWR과 MWR의 분리

일별 스냅샷 인프라가 이미 있으므로 추가 데이터 없이 구현 가능하다.

- **TWR(시간가중)**: 스냅샷 구간별로 `(기말가치) / (기초가치 + 당일 순입금)`을 Modified Dietz로 계산해 기하 체이닝. "운용을 잘했는가"에 답한다.
- **MWR(금액가중)**: 현금흐름 전체에 대한 XIRR(뉴턴법)을 `portfolio-core.js`에 순수 함수로 추가. "내 돈이 얼마나 불었는가"에 답한다.
- UI에서 두 숫자를 **이름 붙여 구분**해서 보여준다. 이 구분 자체가 스프레드시트 대비 이 앱의 차별점이 된다.
- **골든 테스트**: 손으로 검산 가능한 시나리오(입금 1회 + 상승, 중간 입금 + 하락 등)의 기대값을 고정하는 테스트를 도메인 테스트에 추가한다. 수익률 코드는 회귀가 조용히 일어나는 대표 영역이다.
- 환율 분해: KRW 기준 수익 중 "종목 수익"과 "환율 효과"를 분리 표시한다. 데이터는 이미 있다(스냅샷에 fxRate 저장 중).

### 축 3: 동시성과 데이터 안전 — 조용한 소실의 제거

- **낙관적 동시성 제어**: state에 `revision`(정수) 필드를 추가하고, PUT 시 클라이언트가 마지막으로 읽은 revision을 함께 보낸다. 불일치 시 409를 반환하고 클라이언트는 최신 상태를 다시 읽어 재적용한다. Supabase 경로도 동일하게 `updated_at` 조건부 update로 처리한다.
- **세대 백업**: 저장 시 직전 상태를 히스토리로 N세대 보관한다(로컬: `app_state_history` 테이블, Supabase: 히스토리 테이블 + 보관 기간). "어제로 되돌리기"가 가능해지면 blob 모델의 최대 약점이 보험을 갖는다.
- **스냅샷 backfill**: cron/로컬 루프 시작 시 마지막 스냅샷 이후의 영업일 갭(`market-calendar.js` 활용)을 감지하고, Yahoo history API(`api/yahoo/history.js` 이미 존재)로 종가를 받아 소급 생성한다. 소급 생성분은 `backfilled: true`로 표시한다.
- **정합성 자가검증**: 저장 시마다 "총자산 = Σ계좌별 합계" 불변식을 검사하고, 불일치 시 UI에 데이터 품질 배지를 띄운다. 09 문서의 "차이 0원" 기준을 일회성 검증에서 상시 검증으로 승격한다.

### 축 4: 시세 소스 견고화

Yahoo 비공식 API는 언제든 끊길 수 있는 외부 의존이다.

- `market-data-service.js`를 provider 인터페이스로 형식화: `fetchQuote(symbol)` 구현체를 Yahoo → 폴백(국내: Naver 금융/KRX 정보데이터시스템, 해외: Stooq 등) 순으로 시도한다.
- 캐시 티어링: 메모리 캐시 → DB 최근가 → 전일 종가 순으로 강등하되, **항상 출처와 시각을 함께 표시**한다. "오래된 가격을 오래된 것으로 보여주는 것"이 "가격이 안 뜨는 것"보다 낫다.
- 환율도 동일 구조를 적용한다.

### 축 5: 프론트 아키텍처의 결단

vanilla 본체 + React/Craft.js 섬의 이중 스택은 어느 쪽으로든 결단하는 것이 현상 유지보다 낫다.

- **옵션 A — React로 통일**: Craft.js와 빌드 파이프라인이 이미 있으므로 뷰 모듈을 하나씩 컴포넌트로 포팅한다. 대시보드 커스터마이징을 핵심 가치로 키울 거라면 이쪽.
- **옵션 B — vanilla 유지 + Craft.js 제거**: 위젯 순서/크기/표시 여부만 필요하다면 CSS grid + 간단한 설정 UI로 충분하다. React 의존과 번들을 통째로 덜어낸다. 유지비 최소화가 목표라면 이쪽.
- 판단 기준은 "대시보드 에디터가 실제로 얼마나 쓰이는가"다. 사용 로그를 잠깐 남겨 확인하고 결정하는 것을 권한다. 어느 쪽이든 "상태 변경 → 구독 뷰 재렌더"의 단일 렌더 루프를 형식화해서 현재의 수동 재렌더 호출 패턴을 정리한다.

### 축 6: 제품 방향의 갈림길 — 개인 도구 심화 vs 공개 SaaS

- **경로 1: 개인/가족 도구의 완성** — PWA 오프라인 지원, 다기기 동기화(축 3이 전제), 투자자별 뷰 강화, 내보내기 완전성(원장 포함 전체를 언제든 들고 나갈 수 있음). 리스크 낮고 현재 사용 패턴과 일치한다.
- **경로 2: 공개 SaaS** — RLS 감사, Yahoo proxy rate-limit과 쿼터, 비용 모델, 금융 데이터 취급에 따른 개인정보 요건, 온보딩 완성도. 09 문서의 제품 레벨 조건에 더해 운영 부담이 상수로 붙는다.
- **권장**: 경로 1을 먼저 완성한다. "혼자 쓰기에 완벽한 도구"의 품질 기반(동시성, 백업, 데이터 품질, 자동화 신뢰)이 그대로 SaaS의 전제 조건이므로, 경로 1은 경로 2를 배제하지 않고 준비시킨다.

### 축 7: 관측성 — 자동화를 믿게 만드는 것

- 자동화 실행 이력을 구조화해 저장한다: 실행 시각, 트리거(cron/수동/로컬), 성공/부분실패/실패, 실패 종목 목록. 현재 `priceUpdateLogs`를 실행 단위 로그로 승격한다.
- **실패 우선 알림**: Telegram 채널이 이미 있으므로, 성공 요약보다 "오늘 스냅샷이 안 만들어졌다", "이 종목 가격 갱신이 3일째 실패 중이다"를 먼저 보낸다. 자동화의 가치는 성공을 알리는 게 아니라 실패를 놓치지 않게 하는 데 있다.

### 축 8: 테스트 전략 심화

- **속성 기반 테스트**: 도메인 계산에 불변식 테스트를 추가한다 — "입금은 수익률을 바꾸지 않는다(TWR)", "환율 1.0이면 KRW 합계와 USD 합계가 같다", "원장 replay 결과는 순서가 같으면 결정적이다" 등.
- **3환경 계약 테스트**: 같은 state 입력에 대해 브라우저 번들, `server.mjs`, Vercel 함수가 동일한 스냅샷을 산출하는지 검증한다. 공유 도메인 레이어의 약속을 테스트로 고정한다.
- **마이그레이션 골든 테스트**: 버전 N 상태의 골든 파일을 두고 N→N+1 마이그레이션 결과를 고정한다. 축 1의 v7 마이그레이션이 첫 대상이다.

## 비목표 — 명시적으로 하지 않는 것

- **매수/매도 추천, 종목 스코어링, 수익 예측 제시**: CLAUDE.md의 제약을 유지한다. 시뮬레이터도 "과거 시나리오의 교육적 재생"으로 한정하고 미래 수익 제시로 확장하지 않는다.
- **증권사 실계좌 API/스크래핑 연동**: 약관·보안 리스크 대비 이득이 작다. 수동 입력 + 원장 + XLSX 보조 이관을 유지한다.
- **실시간 호가**: 이 앱의 정체성은 "일 단위의 신뢰 가능한 기록"이다. 실시간성은 다른 제품의 일이다.
